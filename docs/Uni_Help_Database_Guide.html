1. The short answer

Say this in class: "Uni Help does not use a SQL database such as MySQL. Its knowledge base is a folder of 36 document files. At start-up the program reads them, cuts them into 313 passages and builds two search indexes in memory: a keyword index and a vector (meaning) index. The vectors are cached in one NumPy file. For a collection this size, that is faster and simpler than running a database server."

If asked "why no database?": the data is small (about 170 KB of text), it is read-only while the chatbot runs, and keeping it as plain files means anyone can open, edit and review a document in a text editor, and every answer can be traced to a file. The design is a file-based knowledge base. A real database would be the next step if the corpus grew to hundreds of thousands of passages (see section 8).

3. The knowledge base: 36 documents

3.1 Two groups

  • 18 official documents (header says origin: official), written from public pages. 11 are about Lovely Professional University (LPU), from lpu.in and LPU's Prospectus 2026. 7 are CSE subject syllabi from AICTE's official model curriculum (LPU does not publish its own syllabi). Each one ends with the exact web page it came from, and the header has a source: line.
  • 18 sample documents for a made-up university, Sutlej Valley University (SVU). They were written for this project so it could be built and tested without confidential papers. The 130 test questions and the 1,027 training examples are about these.

The website shows the group as a label: "Official source" or "Sample". When a question names a university ("at LPU", "at SVU"), only that university's documents are searched.

3.2 What a document file looks like

A document is a markdown text file with a small header between --- lines (called front matter), then headings and text. The program (app/ingest.py) reads the header for the id, title and category, and cuts the text at the headings.

---
title: Attendance Regulations
category: regulations
doc_id: REG-01
updated: 2026-07-01
---
# Attendance Regulations

## 1. Minimum attendance requirement

Every B.Tech student at SVU must have at least 75% attendance in each course ...

## 2. Condonation of shortage

If attendance in a course is 65% or more but below 75%, the student can apply ...

Official documents have two extra header lines:

---
title: LPU Attendance, Examination and Grading Rules
category: regulations
doc_id: LPU-REG-01
origin: official
source: https://www.lpu.in/lpu-assets/download/prospectus/guidelines-and-application-forms-part-c.pdf
---

4.2 A test question (data/eval/questions.jsonl)

{
 "id": "Q001",
 "question": "what happens if my attendance is below 75?",
 "type": "answerable",
 "style": "colloquial",
 "category": "regulations",
 "gold_doc_ids": [
  "REG-01"
 ],
 "gold_section": "2. Condonation of shortage",
 "reference_answer": "If attendance in a course is 65% or more but below 75%, ...",
 "key_facts": [
  "65%",
  "medical certificate"
 ]
}

type is answerable or unanswerable (the chatbot should decline). style is direct, paraphrase, colloquial or hinglish. gold_doc_ids and gold_section name the right passage; key_facts are the strings a correct answer must contain. Counts: 130 questions = 98 answerable (22 direct, 26 paraphrase, 30 colloquial, 20 Hindi-English) + 32 out of scope.

5. How data moves through the system

Filesdata/corpus + uploads
Readload_all_documents()
Cutchunk_document()
313 passages
IndexBM25 (words) +
vectors (meaning)
SearchIndex.search()
top 4 passages

All of this happens in memory when the server starts and again after every upload or delete (Engine.rebuild()). The only thing saved to disk in between is the vector file, so the slow step (computing vectors) is skipped when the documents have not changed. The file name contains a fingerprint (hash) of the passage texts and the embedding model name; if either changes, a new file is made and the old one deleted.

6. Adding, changing and removing data

I want to ...Do thisWhat happens
Add a documentUpload it on the Documents page, or put a .md file in data/corpus/<category>/ and restartIt is validated, cut into passages and indexed. The chatbot can answer from it at once. Uploads are saved in data/uploads/.
Change a documentEdit the file (or upload one with the same name) and restartThe passages and the vector file are rebuilt. Computing the vectors takes from tens of seconds to a couple of minutes on this laptop's CPU.
Remove a documentDelete an uploaded one on the website, or delete the file from data/corpus/Shipped documents cannot be deleted from the website, only by hand.
Mark a document as officialAdd origin: official and source: <url> to its headerThe website labels it "Official source".

7. Why the numbers are what they are

  • 313 passages from 36 documents: most sections stay whole (one section = one passage). Only sections over 220 words are cut into 160-word windows; none of the new LPU or AICTE documents needed it.
  • 384 numbers per vector: the size of the output of the embedding model BAAI/bge-small-en-v1.5. 313 x 384 numbers x 4 bytes is about 0.48 MB, which is why a plain NumPy file is enough.
  • 308 MB model file: 76,961,152 numbers (the model's parameters) x 4 bytes each.

8. If the examiner asks about a real database

Would you use SQL, MongoDB or a vector database?

For this size, no. If the project grew, the natural design would be: PostgreSQL with the pgvector extension (one database for the documents, their metadata and the vectors, with a table such as passages(chunk_id, doc_id, category, section, text, origin, embedding vector(384))) or a dedicated vector store such as FAISS or Chroma. The code that would change is only Index in app/retrieval.py; the rest of the pipeline would stay the same.

How is user data protected?

Conversations stay in the visitor's browser. The server stores only the thumbs-up/down feedback (question, answer, helpful or not, which answer mode). Uploads and feedback are excluded from git. There is no login in this version.

What if a document changes while the server runs?

Uploads and deletes through the website rebuild the index at once, guarded by a lock so two rebuilds never run together. Edits made directly to files in data/corpus/ need a restart.

Where is the data backed up?

The documents, questions and training data are committed to git (GitHub). The model weights and the vector cache are not: the vectors are rebuilt automatically, and the model is recreated with train_local_model.bat (about 75 minutes).

Counts come from the running corpus (build_chunks()) on 27 November 2026. The full list with source links is in docs/Uni_Help_Document_Catalogue.csv.
