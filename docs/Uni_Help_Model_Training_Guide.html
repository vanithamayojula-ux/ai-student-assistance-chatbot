1. What the model is, in plain words

Say this in class: "Uni Help can write its answers in four ways. One of them is our own small language model. We started from FLAN-T5-small, an open model from Google that already understands English, and fine-tuned it on 1,027 examples so that it learned one job: read a student's question and three passages from the documents, write a short answer that uses only those passages, add a citation like [1], and say NO_ANSWER when the passages do not contain the answer. It runs on this laptop's CPU, with no internet and no API key."

1.1 Where the name comes from

  • Transformer is the kind of neural network behind modern language models. T5 ("Text-to-Text Transfer Transformer") is a Google model that treats every task as text in, text out: a question and context go in as text, the answer comes out as text.
  • FLAN means the model was additionally trained on a large collection of tasks written as instructions, which makes it good at following instructions such as "answer using only the context".
  • small is the size: 76,961,152 parameters. For comparison, the models behind ChatGPT, Gemini and Claude are many hundreds of times larger. Small means it runs on a laptop, but it makes more mistakes.
  • svu in the folder name models/svu-flan-t5 stands for Sutlej Valley University, the made-up university it was trained on.

1.2 How it fits into Uni Help

The model is the G (generation) step of RAG. It does not search anything and does not remember the documents. The retriever finds the passages first (Index.search()), then app/local_model.py hands the best 3 to the model. This matters: the model learned a skill, not facts. That is why it can also answer from documents it never saw in training, such as the LPU documents (section 8).

2. Seven ideas you need

WordMeaning
ParametersThe numbers inside the model that decide what it writes. FLAN-T5-small has 76,961,152. Training means adjusting them. They are stored in the 308 MB file model.safetensors (76,961,152 x 4 bytes).
TokenA word or piece of a word. The model reads and writes tokens. Our inputs are about 495 tokens long on average (longest 662), because they contain the question and three passages.
Pre-training vs fine-tuningPre-training teaches a model language from huge amounts of text (Google did that). Fine-tuning continues training the same model on a small set of examples of our task. We only did fine-tuning.
LossA number saying how wrong the model's answers are on the training examples. Lower is better. Ours fell from 1.56 to 0.29.
EpochOne full pass over all 1,027 training examples. We trained for 4 epochs.
BatchA small group of examples processed together (8 here). The model's numbers are adjusted once per batch.
Learning rateHow big each adjustment is (0.0005). Too big and training becomes unstable; too small and it learns too slowly.

3. The training data

3.1 What one example looks like

Every example has an input (what the model reads) and a target (the answer we want it to write).

input:  question: What is the minimum attendance required? context: [1] Attendance Regulations - 1. Minimum attendance requirement: Every B.Tech student at SVU must have at least 75% attendance in each course ... [2] Attendance Regulations - 2. Condonation of shortage: If attendance in a course is 65% or more but below 75% ... [3] ...

target: Every B.Tech student at SVU must have at least 75% attendance in each course in a semester. [1]

The format is built by build_input() in app/local_model.py, the same function used when the chatbot answers a real question. So the model is trained on exactly what it will see in use.

3.2 How the 1,027 examples were made (training/data.py)

  1. 990 questions were written from the 18 sample documents (810 that the documents answer, 180 that they do not), each with the correct answer and the section that holds it. They are in four styles that students really use: direct, reworded, casual and Hindi-English. The questions and answers were written by an AI assistant (Claude) from the documents, not collected from real students.
  2. Every question is sent through the real retriever, so the passages in the input are what the chatbot would really find: the right passage mixed with related wrong ones, in retrieval order.
  3. Bad rows are dropped: 61 questions whose answer passage was not retrieved, 17 that shared 70% or more of their words with a test question, and 9 duplicates. 732 answerable and 171 out-of-scope questions were kept (810 - 61 - 17 = 732; 180 - 9 = 171).
  4. Four kinds of examples are made, so the model also learns when not to answer:
KindCountWhat the passages areTarget the model must write
answer344right passage among the retrieved onesthe answer + [n] pointing at the passage that holds it
shuffled388the same, but in random orderthe answer + [n] (so the citation follows the passage, not its position)
removed124the answering passage taken out, only near-misses leftNO_ANSWER
outside171a question the documents do not coverNO_ANSWER

By wording: direct 468, Hindi-English 184, casual 192, reworded 183. Each of the 18 sample documents contributes 41 to 56 examples.

Important for questions: the training data comes only from the 18 sample documents of the made-up university. The LPU and AICTE documents added later were not part of training.

3.3 Keeping the test fair

  • The 130 labelled test questions are never used for training. A training question sharing 70% or more of its words with a test question is removed (17 were).
  • The test questions are split into a dev half (used to choose the best epoch) and a test half (only used for the final score). The test half played no part in training or choosing.

4. How the training works (training/train.py)

4.1 The loop, in four steps

Each pass through the data repeats these steps for every batch of 8 examples:

1. Predictthe model writes the target one token at a time
2. Measureloss = how far each token was from the target
3. Learnwork out which of the 77 million numbers to nudge (backpropagation)
4. Updatenudge them a little (AdamW optimizer)

In code: loss = model(**batch).loss, loss.backward(), optimizer.step(), schedule.step(), optimizer.zero_grad(). After each epoch, the model answers the dev questions and its score is recorded. The version with the best dev score is saved to models/svu-flan-t5/.

  • Training loss fell every epoch (0.85, 0.53, 0.40, 0.31): the model fitted the training examples better each time.
  • Dev accuracy went 47.7%, 43.1%, 55.4%, 60.0%. It dipped in epoch 2, then rose. The dev set has only 65 questions, so one question is worth 1.5 points and small dips are noise.

5. How the model answers a question (app/local_model.py)

  1. passages_of() keeps the top 3 retrieved passages.
  2. build_input() turns the question and passages into the input text (tables are flattened to one line because the model cannot read line breaks).
  3. generate() turns the text into tokens, the model writes up to 96 tokens using beam search (it explores 4 candidate answers side by side and keeps the best), then the tokens become text.
  4. If the answer is NO_ANSWER, the student sees the polite decline message.
  5. unsupported_numbers() checks that every number in the answer also appears in the passages. If not, the answer is thrown away and the chatbot quotes the documents instead. This is a guard against invented fees and dates.
  6. tidy() removes any citation like [5] that points at a passage that does not exist.

Before any of this, the confidence gate still applies. For language-model modes it uses a looser threshold (0.34), because the model can decline by itself.

7. Limits (say these before you are asked)

  • It is small and not perfect: on the held-out questions about 32.6% of answerable questions got a wrong answer and 10.2% were wrongly declined.
  • The number check only catches invented numbers. In the tests it flagged none, while 28 of the 70 answers checked were still wrong (the model copied a real number from the wrong sentence).
  • Trained on AI-written examples about one fictional university, not on real student questions. The test measures new questions about the same documents.
  • The training set is small (1,027 examples) and the model was trained once (one random seed, 4 epochs). Another run would give somewhat different numbers.
  • The test sets are small (65 and 24 questions), so differences of a few points are within the noise.
  • No memory of the conversation: follow-ups work only because the chatbot searches them together with the previous question.
  • Slower than quoting: about 1.7 s per answer against about 0.2 s.

8. The LPU documents were not in training

After the LPU and AICTE documents were added, the same 32-question smoke test was run with the local model (27 November 2026). It had never seen these documents or this wording.

For comparison, the quote-only mode scored 100% of answerable and 60% of out-of-scope on the same questions. So the local model does generalise to unseen documents, but it declines too often on some answerable questions (hostel and mess charges, Hindi-English questions) and sometimes copies the wrong passage. The numbers are from only 32 questions.

How to improve it (future work): add LPU questions to the training data and retrain (about 75 minutes), train for more epochs, and add real student questions. None of this was done.

9. Likely questions and answers

What model did you use and why that one?

Google's FLAN-T5-small (77 million parameters). It already follows instructions, it is open, and it is small enough to fine-tune and run on a laptop CPU without a graphics card.

Did you train the model from scratch?

No. Training a language model from scratch needs huge data and many GPUs. We fine-tuned an existing model for one task, using 1,027 examples. The pre-trained knowledge of English is Google's.

What does the model actually learn from your data?

A skill, not facts: read the passages it is given, copy the relevant fact, cite the passage number, and answer NO_ANSWER when the passages do not contain the answer. The facts come from retrieval at question time, which is why new documents work without retraining.

Where did the training data come from?

We wrote 990 questions with answers from the 18 sample documents (an AI assistant wrote them, from the documents), ran each through the real retriever to get realistic passages, and built 1,027 examples, including cases where the right reply is NO_ANSWER.

How do you know it is not just memorising?

The 130 test questions were never used in training (near-copies were removed). It was tested on the held-out half (58.5%, against 15.4% before training), on a document that was not in the corpus (70.8%), and on the LPU documents (70.4% of answerable questions).

What is an epoch, and why 4?

An epoch is one full pass over the training examples. We used 4 because the dev score was still improving and each epoch costs about 17 minutes on a CPU. More epochs were not tried.

What is overfitting?

When a model fits its training examples so closely that it does worse on new ones. We watch for it with the dev questions after every epoch and keep the best epoch. Here the dev score kept rising, so no sign of it was seen, but the set is small.

How does it avoid making up numbers?

After the model writes an answer, every number in it is looked up in the passages. If one is missing, the answer is discarded and the chatbot quotes the documents instead. It does not catch a real number copied from the wrong place.

Why also offer Gemini and Claude?

They write more fluent answers but need the internet and a paid API key, and send the question and passages to a cloud service. The local model keeps everything on the computer. The "quote the documents" mode is the safe default because it cannot invent anything.

Could it run on a phone or a website?

Not in the browser. The model file is 308 MB and needs PyTorch, so it runs wherever the Python backend runs. The models/ folder is not stored in git, so a deployed copy would need the folder copied to the server (or retrained there).
